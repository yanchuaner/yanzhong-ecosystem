# 燕中生态计费与账本

本文定义由生态承担成本的请求如何预留、结算、退款和对账。`api_yanchuaner` 是唯一写入者；AI 使用层、客户端、LiteLLM 和供应商适配器都不能修改用户余额。

## 不变量

1. 未持久化预留，不向付费上游派发请求。
2. 一个 `request_id` 只有一个业务终态：`settled`、`refunded` 或 `reconciliation_required`。
3. 流水只追加；余额、Token quota 和仪表盘数字都是可重建投影。
4. 每次状态转换由 `request_id + operation` 或明确幂等键保护。
5. 金额、额度和计量不使用浮点真值；转换规则和价格版本可追溯。
6. 结果不确定时进入待对账，不自动假设成功或全额退款。
7. 重试、故障切换和客户端断连不能产生第二次业务扣费。
8. 公益、活动、legacy 与未来 BYOK 资金来源不静默互相借用。

任何违反上述不变量的路径保持关闭，即使供应商调用本身可用。

## 领域对象

| 对象 | 职责 | 真值 |
| --- | --- | --- |
| Subject | 主站主体在 API 的稳定映射 | 主站 `sub` 映射 |
| Credential | Key/grant 的哈希、应用、状态和有效期 | API |
| Policy | scope、能力、模型、IP、预算、速率与并发 | API |
| Entitlement | 可用资金来源、金额、有效期和使用范围 | API |
| ModelRequest | 一次付费业务请求及其状态 | API |
| ProviderAttempt | 对某个供应商/渠道的一次派发尝试 | API |
| LedgerEntry | 预留、结算、退款、发放、调整和核销流水 | API，只追加 |
| BalanceProjection | 按资金账户聚合的可用/预留余额 | 可从流水重建 |
| ReconciliationCase | 用量或费用结果不确定的处置单 | API |

`ModelRequest` 与 `ProviderAttempt` 分离。一次业务请求可在确认前次尝试未产生费用时切换渠道，但所有尝试共享原业务 `request_id`、预留和幂等语义。

## 标识

- `client_request_id`：客户端对同一用户意图的幂等标识。
- `trace_id`：一次用户操作或工作流运行的跨服务关联。
- `request_id`：网关创建的单次付费业务请求，也是账本关联主键。
- `attempt_id`：一次供应商派发尝试。
- `upstream_request_id`：供应商返回的诊断标识，不作燕中账本主键。
- `ledger_entry_id`：不可变流水项。
- `reconciliation_case_id`：待对账处置单。

任何日志或界面不得把会话 ID、SSE 连接 ID 或上游请求 ID 称为账单请求 ID。

## 请求状态机

```text
accepted
   |
   v
reserved
   |
   v
dispatched
   |---------------------> settled
   |---------------------> refunded
   `---------------------> reconciliation_required

accepted/reserved -- pre-dispatch failure --> refunded
```

### accepted

鉴权、schema、scope、能力和基础策略检查通过，服务端生成 `request_id`。此时尚未调用供应商。

### reserved

在一个事务中选择资金账户、写入预留流水并更新投影。预留记录价格版本、估算用量、最大金额、资金来源和有效截止。余额不足时请求在派发前失败。

### dispatched

写入 ProviderAttempt 后才发送上游请求。派发记录渠道、适配器版本、能力映射和开始时间，但不包含供应商密钥或消息正文。

### settled

上游结果和标准化实际用量明确。结算写入实际费用、释放未使用预留，并保存价格与计量证据。部分成功按可证明的实际用量结算，不机械全额退款。

### refunded

请求未产生费用，或供应商明确确认零消费。退款引用原预留，释放对应资金账户；不能创建独立“赠送”来抵消错误扣费。

### reconciliation_required

断流、超时、供应商状态不明、计量缺失或多次尝试可能产生费用时进入。账户保留有界预留，创建处置单并告警。对账完成后以新的只追加流水结算或退款，不改写历史。

终态记录后，同一操作的重复回调返回既有结果。不同终态竞争时以数据库约束拒绝第二次提交并产生安全告警。

## 预留与结算

估算基于已发布价格版本、能力限制和请求上限。所有乘数先校验边界，再使用安全的整数或 decimal 转换。NaN、无穷、溢出、负值或超过数据库范围直接拒绝或饱和并写管理员可见审计，不产生负费用。

结算保存：

- 标准化输入、输出、缓存、图片、音频时长等实际计量；
- 供应商原始计量的受限证据与适配器版本；
- 燕中价格版本、汇率版本、计算表达式版本和最终整数金额；
- 预留、实际、释放或追加差额；
- `request_id`、`attempt_id` 和可用的 `upstream_request_id`。

供应商价格和燕中用户权益是两套口径。LiteLLM 或供应商成本用于核对，不直接成为用户账本写入。

## 资金来源

| funding source | 用途 | 默认回退 |
| --- | --- | --- |
| `public_benefit` | 生态公益额度 | 不借活动或 BYOK |
| `campaign` | 指定活动、能力、模型或期限 | 不匹配时按明确策略拒绝或选择公益 |
| `legacy` | 迁移前兼容余额 | 仅按已登记迁移策略使用 |
| `byok` | 用户自带供应商凭据产生的外部费用 | 不从公益账本扣供应商成本 |

资金选择在预留时固定。跨来源拆分必须在策略中显式允许，并为每个来源写独立流水；结算和退款按原比例回到原账户。过期、冻结和限定模型的权益不能由管理员界面或旧 Token 写入口绕过。

## 幂等、重试与故障切换

- 同一主体、应用和端点的 `client_request_id` 在幂等窗口内映射到同一业务结果。
- 客户端超时后先查询请求状态，不盲目创建新请求。
- 供应商 429、5xx 或网络错误只在请求可重放、前次未消费且适配器明确允许时重试。
- 流式响应已经输出内容或上游计量不明时，不自动切换供应商。
- 每次尝试有独立 `attempt_id`，但不得新建第二次资金预留。
- 重试次数、渠道序列和停止原因进入观测，不记录正文。

## 流式与取消

SSE 连接断开只表示消费者离开，不能推导供应商未消费。网关传播取消并等待有界确认：

- 上游确认取消且无计量：退款；
- 上游返回部分用量：按实际结算；
- 无法确认：待对账。

客户端收到断流后显示“结果待确认”，并通过 request status 查询，不在本地恢复额度。业务终态写入与 HTTP/SSE 连接生命周期分离。

## 异步、媒体与任务

异步能力必须在派发前持久化任务 ID、预留、回调鉴权、轮询状态和取消策略。完成回调按事件 ID 幂等；任务超时不等于供应商取消。

开启一种新计费单位前必须具备：

- 请求上限和可信计量来源；
- 价格、取整、最小费用和汇率版本；
- 预留估算与实际结算；
- 回调重放、取消、部分结果和状态不明处理；
- 供应商账单样本与故障测试。

缺少任一项时，该能力可以在用户明确 BYOK 且不进入公益账本的隔离路径验证，但不得伪装成平台计费完成。

## 管理员发放与调整

发放、增加、减少、冻结、过期和纠错都写不可变流水。请求至少包含目标、资金来源、整数金额、原因、操作者、幂等键和外部凭证摘要。覆盖余额只能实现为“计算差额并追加调整”，不能直接改历史流水或静默更新投影。

高风险批量操作先返回不含密钥和隐私的预检，执行时指定明确对象、小批量和原因。失败可重试但不重复发放。

## 投影与对账

余额投影至少区分 available、reserved、spent、refunded 和 expired。后台任务持续检查：

- 流水聚合是否等于余额投影；
- `reserved`/`dispatched` 是否超过允许时长；
- 终态请求是否存在且只存在一组匹配流水；
- 供应商用量或账单与 ProviderAttempt 是否可关联；
- 重试或回调是否产生重复费用；
- 价格、汇率和适配器版本是否完整。

对账修复追加带原因和关联 case 的流水，不修改或删除原记录。自动修复仅处理可证明的确定性差异，其余进入人工队列。

## 错误语义

| 错误 | 含义 | 客户端动作 |
| --- | --- | --- |
| `quota_exhausted` | 允许的资金来源不足 | 不重试，展示额度入口 |
| `policy_denied` | scope、模型、IP、期限或预算不允许 | 不换 Key 绕过 |
| `billing_unavailable` | 无法安全预留或写流水 | 不向上游派发，稍后重试 |
| `request_in_progress` | 同一幂等请求仍在处理 | 查询原 request ID |
| `request_pending_reconciliation` | 费用结果不确定 | 显示待确认，不本地退款 |
| `usage_invalid` | 上游计量无法安全结算 | 停止扩大调用，进入对账 |

错误文案不参与程序判断。认证失败、额度不足、供应商故障和账本故障必须分别编码。

## 可观测与隐私

计费状态、延迟、资金来源、能力、公开模型别名、价格版本和错误码完整记录；消息正文、知识片段、Authorization、Key、Cookie、供应商 Secret 和完整请求体不记录。

计费与安全事件不采样丢失。面向用户的流水只显示其有权查看的金额、能力、时间、状态和 request ID；内部渠道、成本底价和管理员备注按权限隔离。

## 验收矩阵

- 并发请求不会超支、负余额或重复预留。
- 客户端重试、网关重启和重复回调保持幂等。
- 上游 400、401、429、5xx、连接失败、首段前超时、输出后断流和取消均得到确定或待对账终态。
- 故障切换不会让两个供应商同时产生未核对费用。
- Redis、主库、日志库或账本服务不可用时不派发新付费请求。
- SQLite、MySQL 和 PostgreSQL 的约束与事务结果一致。
- 流水可以重建余额投影，供应商样本可按 request/attempt 对账。
- 异步、图片、音频、视频和批处理分别通过真实计量与故障验收后才启用平台计费。
