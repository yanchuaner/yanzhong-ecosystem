# 燕中生态维护责任

本文登记子系统责任类型和当前治理缺口，不公开个人隐私或生产权限细节。具体个人账号、轮换材料和应急通讯录应放在受限运营记录；公开仓只登记可验证的 GitHub 团队或角色联系方式。

## 责任矩阵

| 子系统 | 责任范围 | 主要责任角色 | 必备备份角色 |
| --- | --- | --- | --- |
| 生态治理 | 架构、schema、ADR、许可、品牌和阶段真值 | 生态维护者 | 至少一名跨仓复核者 |
| 主站 | 身份、成员、内容、活动、生产数据与 OIDC | 主站 owner | 身份/恢复备份维护者 |
| 燕中 API | YanCore、策略、网关、计费、账本、上游同步 | API owner | 账本与上游升级备份维护者 |
| 燕中 AI | 使用层、会话、角色、知识、记忆、工作流和 BFF | AI owner | 数据迁移与发布备份维护者 |
| 小程序 | 微信客户端、契约映射、设备与隐私验收 | 小程序 owner | 主站 API 联络人 |
| Lab | 内容、来源、双语、设计和发布 | Lab owner | 内容审核备份维护者 |
| YCZX Code | Agent 核心、Provider、Tool、Policy 和发布包 | CLI owner | 安全策略备份维护者 |

## 当前登记状态

截至 2026-08-13，治理仓已用 `CODEOWNERS` 将评审路由到 `@yanchuaner`，但仍是单账号且没有公开备份角色；七个项目的公开 owner、备份联系人、支持版本和升级路径仍未完整登记。仓库规则、评审路由和私密漏洞报告入口不能替代维护责任分配。

该缺口的处理要求：

1. 将治理仓当前单账号路由迁移到至少包含主责与备份的 GitHub 团队，不在公开文档写私人手机号、私人邮箱或生产账号。
2. 每个 Preview 仓库登记一个主要 owner 和至少一个可接手角色；人员不足时明确单点风险和停止服务条件。
3. 生产权限、Secret 轮换、备份恢复和安全响应分别登记主责与备份，不全部依赖同一账号或设备。
4. CODEOWNERS 只表达评审路由，不自动授予生产、发布或法律决策权限。
5. 人员变化与项目阶段变化在同一 PR 更新本文件、目标仓责任文件和受限运营通讯录。

在上述登记完成前，任何项目不得升级为 Stable，也不得宣称具备完整交接能力。

## Owner 职责

- 维护模块边界、公共契约、迁移和兼容策略；
- 评审身份、账本、隐私、来源和生产风险；
- 保持最低测试、发布、观测、备份与回滚证据；
- 处理依赖与上游升级、漏洞披露和弃用；
- 在无法继续维护时启动交接、降级或归档，而不是停止响应。

Owner 不单独取得贡献者版权，也不能绕过已发布的评审、安全、许可或账本不变量。高风险变更需要非作者复核。

## 交接门禁

交接至少包含：支持范围、未闭环风险、公开契约、数据与迁移、生产拓扑、凭据清单引用、备份恢复、发布回滚、上游来源、许可证、告警和未处理安全问题。Secret 通过受控渠道轮换或转交，不写入交接文档。
