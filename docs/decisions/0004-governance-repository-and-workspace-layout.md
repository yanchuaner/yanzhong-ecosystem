# 0004：独立治理仓与多仓工作区布局

- 状态：已采纳
- 日期：2026-08-13
- 影响：治理真值、项目注册、CI、跨仓开发与契约发布

## 背景

七个代码项目各自拥有独立 Git 历史、依赖、发布和上游关系。生态级 `AGENTS.md`、架构、契约、Schema、品牌、许可和阶段状态此前只存在于共同父目录，没有独立提交历史和 CI。将全部项目合并到一个仓库会混合历史与发布边界；使用 submodule 又会让治理提交承担项目提交指针同步，而不能解决契约消费与合同测试问题。

## 决策

1. `yanzhong-ecosystem` 是生态治理、架构、契约、ADR、项目注册表和阶段状态的唯一写入源。
2. 七个代码项目保持独立仓库、分支、PR、版本、发布权限和上游关系。
3. 完整本地工作区可把项目 checkout 放在治理仓根目录下，但根 `.gitignore` 明确排除这些目录；不使用 Git submodule、subtree 或 vendoring 聚合项目源码。
4. `repos.yaml` 登记正式项目、数据权威、依赖方向和校验入口；阶段与完成度不进入注册表。
5. 校验器提供独立模式和工作区模式。治理仓 CI 只运行独立模式，项目级与跨仓实现验证由完整工作区和各项目 CI 承担。
6. 项目消费公共 Schema 时使用不可变提交或正式版本，不依赖本地父目录的未提交文件。

## 理由

- 独立治理历史使规范、Schema 和 ADR 可以单独评审、回滚和发布。
- 保留多仓边界避免 New API 上游同步、各产品依赖和发布节奏互相污染。
- 注册表比 submodule 指针更适合表达职责、数据权威和依赖方向。
- 双模式校验让独立 PR 保持快速，同时保留完整工作区审计能力。

## 代价

- 跨仓变更需要多个关联 PR，不能依赖单次原子提交。
- 治理 CI 不证明项目消费者已经兼容，必须由合同测试补足。
- 新成员需要根据注册表建立完整工作区，并分别管理项目依赖。
- 契约版本发布和消费者升级需要明确兼容窗口。

## 执行

- 工作区规范：`../governance-repository.md`
- 项目注册表：`../../repos.yaml`
- 协作顺序：`../agent-guide.md`
- 状态真值：`../燕中生态项目关系.txt`

## 回滚

若未来证据证明部分项目必须合并，先以新 ADR 说明共同发布、权限、历史和数据边界，再迁移选定项目。迁移不删除原仓来源、许可证或发布记录，也不通过直接提交嵌套 `.git` 目录完成。
