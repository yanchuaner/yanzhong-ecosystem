# 0002：自主内容统一采用 AGPL-3.0

- 状态：已采纳
- 日期：2026-08-13
- 影响：燕中生态自主代码、原创文档、正式示例和可版权化品牌资产

## 背景

生态项目曾同时出现 MIT、AGPL-3.0 和未明确登记的原创内容。网络服务、客户端、CLI 与教学仓之间缺少统一贡献条件，外部使用者也难以判断源码获取义务。`api_yanchuaner` 同时包含 New API 上游代码及其 AGPLv3 Section 7 附加条款，不能用一份笼统声明覆盖所有来源。

## 决策

1. 燕中生态新创作的代码、原创文档和正式示例默认按 GNU Affero General Public License v3.0 提供，SPDX 表达式使用 `AGPL-3.0-only`。升级到后续许可证版本需要新的权利人授权，不从现有 LICENSE 文本推定。
2. 各正式仓库保留完整 AGPLv3 许可证文本，并在包元数据、README 或 NOTICE 中给出一致声明。
3. `api_yanchuaner` 的上游部分继续适用 New API 的许可证、Section 7 附加条款、版权与署名；本决策不把上游代码重新声明为燕中原创，也不扩大已有授权。
4. 第三方代码、文档、字体、图标、数据、模型和其他素材保持原许可证。无法兼容或无法确认权利的内容不得以仓库总许可证重新授权。
5. 历史版本已经授予的许可证不可撤回。历史内容改为 AGPL 前必须确认实际权利人有权授权；不能确认时，在文件、目录或来源清单中保留原许可证。
6. 网络服务向远程用户提供与当前部署版本对应的源码入口、许可证、修改说明和必要构建信息。
7. 新贡献默认按目标仓库的 AGPL 条件提供；贡献者保留其实际创作部分版权，除非另有明确书面协议。
8. 已有文件明确写明“version 3 or later”时，该文件的既有授权继续有效；`AGPL-3.0-only` 是燕中自主新内容的默认策略，不用于缩减已经授予的权利。

## 理由

- 网络服务的修改也应回馈源码，符合开放生态和可接手维护目标。
- 统一贡献条件减少跨自主仓库复用时的许可歧义。
- 明确第三方例外能同时保护生态自主 IP 与上游权利。
- 使用标准 SPDX 表达式便于包管理器、SBOM 和许可证扫描识别。

## 代价

- 部署修改版网络服务时需要履行源码提供义务。
- 引入依赖、素材和示例前必须检查许可证兼容性，不能只看仓库总许可证。
- 既有 MIT 发布仍可按原许可继续使用，统一政策不能追溯撤销已授予权利。
- `api_yanchuaner` 的附加条款和上游归属需要独立维护，不能只显示燕中版权声明。

## 回滚

已经按 AGPL 发布的版本和贡献不追溯撤销许可。未来若调整新版本许可，必须新建 ADR，核对全部权利人授权、上游兼容、依赖兼容和用户迁移；无完整授权时继续维持本决策。
