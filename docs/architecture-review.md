# 燕中生态架构审查

审查基线：2026-08-13。审查对象包括根级治理文档、七个子仓库、AI/API 关键实现以及 Kirara AI、LiteLLM、New API 的公开架构与许可证。

本文只记录缺陷、风险和收敛顺序。目标架构见 `architecture.md`，跨系统规则见 `contracts.md`，完成状态见 `燕中生态项目关系.txt`。

## 结论

生态已经具备真实身份、网关、计费和 AI 产品链路，但模块化程度落后于功能增长速度。当前最大风险不是功能不足，而是以下临时结构继续成为新功能默认落点：

- AI Web 的页面状态与业务流程集中在单个大型组件中；
- AI BFF 的对话处理器同时负责鉴权、知识、记忆、群聊调度和模型调用；
- API 的燕中领域模块仍嵌在 New API 的兼容 Token、路由和余额结构中；
- 能力目录、错误语义、消息信封和观测字段已有生态级 schema 基线，但尚未接入提供方、消费者与契约测试；
- 文件存储、环境变量和第三方网关配置在部分位置仍被当作业务接口；
- 文档曾混写当前状态、历史 PoC 和目标设计，导致同一组件出现相互矛盾的职责描述。

这些问题应在继续扩展功能的同时逐步消除，不等待 Preview 结束后集中重构。

## 已有基础

| 能力 | 已有基础 | 需要保持的边界 |
| --- | --- | --- |
| 身份 | 主站 OIDC、PKCE、短期授权、身份事件 | 主站继续是唯一身份源 |
| 主体授权 | YanCore grant、短期哈希应用 Key | 协议语义不依赖 New API/Open WebUI |
| 网关 | OpenAI-compatible `/v1`、渠道适配与策略 | 客户端不感知内部渠道和 LiteLLM |
| 计费 | 预扣、结算、退款结构与不可变流水 | API 是唯一账本写入者 |
| AI 产品 | 会话、角色、世界、RAG、记忆、群聊、媒体 | 使用层不自行实现余额和供应商路由 |
| Agent | YCZX Code 已有可安装 CLI 骨架和目标协议文档 | 实现必须统一使用生态网关，不复制供应商适配 |
| 开源治理 | AGPL、NOTICE、来源矩阵、分仓规则 | 品牌替换与第三方归属同时成立 |

## P0：阻止新增耦合

### 发布依赖存在未评估的高危公告

现状：2026-08-13 以当前锁文件执行生产依赖审计，主站未发现已知漏洞；燕中 API、燕中 AI、Lab 与小程序仍报告 high 或 critical 公告。小程序结果集中在 Taro 4.2.0 及其构建/多端依赖，AI 与 Lab 包含 Next.js、PostCSS、Sharp、MDX/YAML 链路，API 前端包含 Markdown 清洗、链接解析及上游工作区依赖。审计严重度不等于实际可利用性，但构建通过也不能替代可达性判断。

影响：未分类公告可能影响公网渲染、非可信 Markdown/MDX、URL 解析、开发服务或供应链构建；直接强制降级或跨主版本升级又可能破坏 Taro、New API 上游同步和现有契约。

处理：

1. 按锁文件、部署产物和实际输入面逐条确认受影响版本、生产可达性、补丁版本与上游状态，区分运行时、构建时和未打包依赖。
2. 可兼容修复通过独立依赖 PR 更新；需要跨主版本迁移的项目保留契约、真实设备/页面回归和回滚产物。
3. 暂不能修复的 high/critical 项必须登记 owner、理由、缓解、影响版本、复核日期和到期日；没有时限的“接受风险”无效。
4. CI 对锁文件运行生产依赖审计并保存 SBOM/报告摘要；公告数据库更新造成的变化按新结果评审，不把固定数量写成长期基线。

退出条件：公开发布产物不存在未经评估的 high/critical 公告；可达风险已修复，确属不可达或暂时接受的项目具备可复核证据、时限和缓解措施。

### API 上游前端没有干净的全量 Lint 基线

现状：燕中改动文件可通过定向 oxlint，前端类型检查和生产构建也能通过；但 `web/default` 的全量 `bun run lint` 仍在未改动的 New API 上游文件中报告 Promise、条件块、嵌套表达式、iframe、类型导入等既有错误。因此 `bun run release:check` 当前会在全量 Lint 或后续依赖审计阶段失败。

影响：新增错误难以与基线区分，上游同步可能继续扩大债务；只运行定向 Lint 会掩盖发布分支整体质量状态。

处理：固定当前上游版本和完整报告，按目录分批清理或与上游同步修复；新增/修改文件保持零错误，CI 同时运行定向检查和全量门禁，不增加永久忽略规则来压低计数。

退出条件：`web/default` 的全量 Lint 在锁定依赖下通过，`release:check` 不再依赖基线豁免；上游升级继续维持零错误。

### 治理仓已独立，契约消费者尚未固定版本

现状：根 `AGENTS.md`、`docs/`、schema、许可和治理文件已经进入独立 `yanzhong-ecosystem` 仓库；`repos.yaml`、独立/工作区双模式校验与治理 CI 已建立。API、AI 与 Web 尚未以不可变提交或版本标签固定所消费的契约。

影响：治理真值已经可评审和回滚，但项目仍可能通过手工复制产生第二份 schema；治理仓通过不能证明消费者合同测试通过。

处理：保护治理仓 `main` 并要求治理 CI；公共契约使用不可变提交或正式版本发布，API 提供方与 AI/Web/CLI 消费者在各自 CI 校验相同 fixture。项目文档链接治理真值，不维护可漂移副本。

退出条件：治理仓 `main` 受保护；至少 API、AI 与 Web 的 CI 固定并校验所消费的契约版本。

### 统一契约尚未进入运行时验收

现状：`docs/schemas/` 已发布身份事件、能力目录、错误信封、消息、工作流、扩展、计费和遥测的 JSON Schema 基线；YanCore 端点已有文档，OpenAI-compatible 接口沿用上游。提供方生成、消费者校验、fixture 和兼容性测试尚未落地。

影响：消费者容易复制响应字段或依赖错误文案；协议升级只能靠人工同步。

处理：

1. 以 `contracts.md` 为语义真值、`docs/schemas/` 为机器可读基线；提供方补齐端点 OpenAPI 和运行时生成/校验。
2. 建立契约测试 fixture，覆盖身份事件、YanCore、模型流式事件和计费状态。
3. 新跨仓字段未进入 schema 前不得被第二个消费者使用。

退出条件：至少 AI Web 与 YCZX Code 对同一能力目录、错误码和 request ID 契约通过自动测试。

### AI Web 页面成为应用控制器

证据：`apps/ai-web/src/app/page.tsx` 约 2300 行，同时维护登录后初始化、会话、角色、世界、额度、Key、媒体配置、语音和群聊流式状态。

影响：任何新视图都会触及共享状态；业务失败与 UI 状态耦合，移动端和未来适配器难以复用。

处理：

1. 先提取有真实消费者的 API client 与领域 action，不创建空框架。
2. 按 `session`、`conversation`、`persona`、`world`、`account`、`media` 拆分状态边界。
3. 页面只组合视图和触发 action；网络响应转换留在 adapter/client。

退出条件：页面不直接拼接业务 API 路径；群聊、单聊和媒体至少通过独立 action/hook 驱动。

### AI 对话处理器职责过载

证据：`apps/ai-web/src/lib/chat-handler.ts` 同时执行会话解析、RAG、长期记忆、群聊调度、提示词构造、网关转发和撤销响应。

影响：无法独立测试或替换工作流步骤；未来 IM 接入只能复制 Web 路由。

处理：定义统一消息信封、上下文贡献者、工作流运行时和能力网关端口。先把现有 `chat`、`roleplay`、`group` 固化为三个版本化内置工作流，再考虑可视化编辑。

退出条件：Web 路由只完成协议适配和调用工作流；知识、记忆和模型调用以显式块或服务参与。

### 计费失败终态尚未完成真实验收

现状：标准同步链路已有预扣、结算与退款代码和局部测试，但真实上游失败、断流、超时、重试和 request ID 对账仍是运行门禁。

影响：重复扣费、未终结预留或错误退款会破坏公益账本可信度。

处理：实现并验证正式请求状态机；建立未终结预留巡检和 `reconciliation_required` 队列；异步/媒体计费在完成前继续 fail-closed。

退出条件：真实故障矩阵通过，任一 `request_id` 恰有一个终态，余额投影可与流水核对。

## P1：形成平台边界

### 燕中控制面依赖上游 Token 结构

现状：YanCore 策略已有独立表与修订，但预算、模型、IP 和有效期仍部分投影到 New API Token 兼容列。

影响：上游升级可能改变燕中业务语义；策略写入存在双模型一致性成本。

处理：建立燕中 `Credential` 与 `Policy` 领域服务，上游 Token 只作为 relay adapter 投影。所有写入先进入燕中事务边界，再投影到兼容层。

退出条件：策略读取和写入不以 New API 控制器/DTO 为领域接口；投影可重建并有一致性检查。

### 能力与模型名称未分离

现状：AI Web 会话直接持有网关下发的模型字符串，知识嵌入通过环境变量选择具体模型。

影响：更换供应商或模型别名会渗透使用层；工作流无法声明抽象能力。

处理：API 发布稳定能力目录；使用层选择 `text.chat.general`、`embedding.retrieval.multilingual` 等能力，模型别名仅作为高级选项或兼容层。

退出条件：默认工作流不包含供应商模型名，渠道切换不修改 AI 领域代码。

### 文件存储缺少正式仓储边界

现状：AI 会话、角色、世界、知识、记忆和设置使用 `/data` 文件存储与进程内锁。

影响：多实例、原子跨实体变更、索引迁移和大规模备份受限。

处理：先定义仓储接口和 schema 版本，再提供当前文件适配器与数据库适配器；不直接把现有 JSON 结构宣布为公共格式。

退出条件：核心领域服务不直接调用文件 API；文件到数据库迁移可在隔离数据上往返验证。

### 可观测性只到 request ID，缺少统一追踪

现状：模型请求已有 request ID 与用量日志，身份和工作流缺少统一 trace 传播；日志字段与告警仍分散。

影响：群聊一次用户操作会产生调度、多个角色、嵌入与记忆请求，难以完整关联成本和失败。

处理：所有入口建立 `trace_id`，每次付费调用生成独立 `request_id`；统一结构化事件、指标和脱敏规则。

退出条件：可从一次用户操作查询全部工作流块、模型请求、结算和失败事件。

## P2：开放扩展能力

### 插件安全模型尚未实现

现状：`extensions.md` 与扩展 manifest schema 已定义来源、权限、资源、网络、审计和生命周期基线；运行时隔离、签名验证、授权界面、紧急停用和卸载清理尚未实现。

风险：若直接引入插件市场，第三方代码会在缺少执行隔离时获得服务器环境、用户内容或网络权限。

处理：先实现静态能力注册表和内置块，再按已发布 manifest 接入签名、scope、资源配额、网络策略、数据访问、升级/卸载和紧急禁用。完整门禁通过前不执行外部插件包。

### 多接入适配器尚未落地

风险：若先为 QQ、微信或 Telegram 单独实现业务逻辑，会形成多套会话和权限语义。

处理：Web 先迁移到统一消息信封，成为第一个真实适配器；第二个入口复用同一工作流与领域服务后，才宣布适配器契约稳定。

### 设施网关存在双层复杂度

现状：New API 和 LiteLLM 都具备部分路由、预算和日志能力。

风险：重复重试、双重路由、成本口径冲突和故障定位困难。

处理：API 控制面拥有最终策略、路由决策和账本；LiteLLM 只承担明确登记的供应商协议/故障能力与成本核对。逐项验证哪些能力仍需 LiteLLM，能由 New API 适配器直接承担的路径不做无意义双跳。

退出条件：每项运行职责只有一个执行者；替换 LiteLLM 的契约测试和回滚说明完整。

## 本轮治理整改

| 原问题 | 已采取的处理 | 后续门禁 |
| --- | --- | --- |
| 阶段文档继续使用过期“当前限制” | 历史文档标注日期与效力；当前事实集中到阶段真值 | 新验收只更新一处状态真值 |
| `roadmap.md` 复制大量完成状态 | 改为能力顺序和退出条件 | 路线文档不得维护第二份完成清单 |
| LiteLLM 被同时描述为“唯一数据面”和“非产品链路” | 统一定义为可替换设施适配器 | 每项运行职责只能有一个执行者 |
| “统一 AGPL”与部分仓库 MIT 声明冲突 | 自主代码与原创文档统一为 AGPL-3.0，第三方保持原许可 | 发布前扫描许可证文件与包元数据 |
| 品牌化被排到功能完成以后 | 改为每个增量同步完成命名、视觉与法律声明 | 禁止新增第三方产品品牌资产 |
| 各项目 AGENTS 粒度差异过大 | 统一定位、所有权、依赖、模块、红线、验证和文档入口 | 项目规则不得重定义生态契约 |
| 跨仓语义只有自然语言 | 发布版本化 JSON Schema 基线 | 接入运行时校验与提供方/消费者契约测试 |
| 根级规范无独立历史 | 建立治理仓、项目注册表、双模式校验与独立 CI | 消费者固定契约版本并运行合同测试 |

## 执行顺序

1. 建立并执行跨系统契约、错误码和追踪字段。
2. 拆分 AI Web 页面和对话处理器，先形成第一个工作流与适配器闭环。
3. 固化 API 请求状态机，完成真实失败退款和对账。
4. 将 YanCore Policy 从上游 Token 结构中进一步独立。
5. 建立能力目录、仓储端口和可观测性导出器。
6. 第二个接入适配器或供应商实现通过契约测试后，再开放插件/工作流扩展面。

每一步都必须保持生产路径可回滚；不得以“平台化”为由暂停已有安全和计费门禁。
