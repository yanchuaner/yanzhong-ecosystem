# 燕中生态开源治理

本文规定生态项目如何立项、维护、贡献、发布、弃用和归档。技术架构见 `architecture.md`，来源与许可证见 `upstream-and-ip.md`，品牌规则见 `brand.md`。

## 治理对象

治理覆盖：

- 燕中组织下的正式代码、文档、设计资产和公开 schema；
- `yanchuaner.cn`、子域、小程序、CLI 和未来 App 的公开产品身份；
- 生态扩展注册表、示例、教程和兼容认证；
- 上游修改、第三方依赖、数据迁移和退役服务；
- 安全披露、发布证据和维护者交接。

生产数据、成员隐私、供应商 Secret 和内部恢复材料不因代码开源而公开。

## 项目阶段

| 阶段 | 含义 | 对外承诺 |
| --- | --- | --- |
| Proposal | 问题、所有者和边界待确认 | 不分配正式域名，不宣称交付 |
| Experimental | 在 Lab 或隔离仓验证 | API、数据和名称可变化，不接生产真值 |
| Preview | 可由少量成员使用、可回滚 | 明确限制、支持范围和退出方式 |
| Stable | 契约、运维和兼容策略已成熟 | 按公开弃用策略维护 |
| Maintenance | 只修安全、数据和关键缺陷 | 不扩展产品范围 |
| Archived | 停止运行和常规维护 | 仓库只读，保留来源与迁移说明 |

阶段由状态真值登记，不由 README 标题、版本号或部署成功自动决定。升阶需要满足相应门禁，降阶和归档同样记录原因、数据处理和用户影响。

## 立项

新仓库、子域或核心模块先提交一页提案，至少回答：

- 服务对象和需要解决的真实问题；
- 与现有项目的职责差异和非目标；
- 身份来源、数据所有者、调用方向和删除方式；
- 是否产生费用、处理未成年人或敏感数据；
- 维护者、最低维护期和停止服务方式；
- 计划使用的许可证、第三方来源和品牌名称；
- Preview 验收和不继续建设的判定条件。

能由现有模块、适配器或工作流解决的问题不另建仓库。需要第二份身份、账本或用户表的提案默认拒绝，除非存在独立法律主体和经 ADR 记录的边界。

## 决策层级

| 决策 | 记录位置 | 审批要求 |
| --- | --- | --- |
| 局部实现与不改变契约的重构 | 项目 PR | 项目维护者 |
| 项目公共 API、数据模型或迁移 | 项目设计文档/ADR | owner 与受影响消费者 |
| 跨仓身份、账本、网关、schema | 根 `docs/decisions/` | 生态维护者与各 owner |
| 新项目、正式域名、Stable/归档 | 状态真值与治理记录 | 生态维护者 |
| 许可证、商标、隐私或高风险数据 | 专项记录 | 负责人确认，必要时法律评估 |
| 生产发布、迁移和回滚 | 发布记录 | 服务 owner 与运维责任人 |

无法达成一致时先保持现有稳定契约，以可回滚实验收集证据。排期压力不构成跳过安全、许可或账本不变量的理由。

## 维护责任

每个进入 Preview 的仓库需要公开维护责任文件，至少登记：

- 当前 owner 和至少一个可接手联系人；
- 代码评审、发布、Secret 轮换和安全响应责任；
- 支持的平台、分支和数据版本；
- 无响应时的升级路径；
- 维护者退出时的交接或归档流程。

当前登记状态与责任角色见 `maintainers.md`。尚未建立项目责任文件或 `CODEOWNERS` 的仓库在升 Stable 前补齐。单一维护者项目明确单点风险，关键恢复材料不只由一人持有。

维护者可以拒绝越权、无测试、来源不明、无法长期维护或偏离项目边界的贡献。拒绝说明可验证原因，不以个人偏好替代已发布规则。

## 贡献

- 贡献者保留其原创部分版权，并同意按目标仓库 AGPL-3.0 提供贡献；书面协议另有约定时除外。
- 提交者确认有权提供代码、文档、设计和素材，并登记直接采用或改编的第三方来源。
- AI 可以辅助实现和检查，但提交者对准确性、来源、许可、安全与验证负责；自动生成不改变版权和来源审查。
- PR 聚焦一个问题，说明行为变化、契约、迁移、测试、观测和回滚。
- 学习记录必须由成员本人完成；实验代码进入正式仓要重新设计和评审。
- 是否引入 DCO 或 CLA 需单独 ADR，不在缺少流程和历史迁移方案时临时强制。

行为规范、Issue 模板和首次贡献路径在公开贡献规模扩大前统一建立；处理成员冲突时保护未成年人和个人隐私，不公开私人材料。

## 评审

评审优先级：

1. 身份、权限、隐私、账本和数据不可逆风险；
2. 跨仓契约与兼容；
3. 正确性、失败语义和测试；
4. 来源、许可证、品牌和公开声明；
5. 模块所有权、维护成本和可观测性；
6. 性能、体验和代码风格。

作者不能以测试通过替代架构与数据边界评审。高风险迁移、计费、鉴权、插件和生产配置需要非作者复核；紧急安全修复可以缩短流程，但修复后补齐记录和回归。

## 版本与发布

- Preview 服务使用 `preview` 运行标签和“日期-短哈希”追溯产物，不用随手递增版本号代替证据。
- 公共 schema、SDK 和可独立消费的包使用明确版本与 changelog；破坏性变化升主版本。
- 发布产物由锁定工具链构建，记录源提交、依赖锁、镜像摘要、schema、迁移和 SBOM/第三方清单。
- 生产服务器不构建源代码；发布前有备份、回滚产物和迁移演练。
- 对外发布同步提供源码入口、许可证、NOTICE、安全报告方式、已知限制和数据删除说明。

发布权限与代码合并权限分离时，二者均使用最小权限和可审计账号。禁止使用个人长期 Token 作为不可替代的生产发布机制。

## 兼容与弃用

公共 API、事件、schema、扩展和数据格式弃用时发布：

- 被弃用项、替代项和停止日期或版本；
- 已知消费者与迁移负责人；
- 兼容读写窗口和使用量观测；
- 数据迁移、备份、回滚和删除；
- 安全原因需要立即停用时的影响和恢复条件。

观测确认无消费者后才删除。无法联系的消费者不自动获得永久兼容，但必须提供合理导出或迁移路径。

## 安全治理

- 各正式仓库维护私密安全报告方式，不要求报告者公开漏洞或真实凭据。
- 收到报告后先确认、分级、限制影响、轮换凭据和保留脱敏证据，再修复与协调披露。
- 安全公告说明受影响版本、影响、修复、缓解和升级方式，不公开可滥用的成员数据。
- 供应链事件同时检查镜像、依赖锁、构建产物、Secret 和历史发布。
- 严重事件可以冻结渠道、Key、扩展或发布，不等待常规迭代。

生态级安全边界见 `security-and-privacy.md`。

## 扩展生态治理

官方扩展注册表只收录通过 `extensions.md` 门禁的分发物。登记内容包括 owner、来源、许可证、签名、权限、兼容版本、支持期、审计日期和紧急禁用状态。

“官方”“社区”“实验”是维护与审核等级，不表示质量背书或授权使用第三方商标。社区扩展不得使用燕中 Logo 冒充官方；兼容标识需遵循品牌规则。下架扩展保留安全公告和数据迁移说明，不静默删除记录。

## 归档与停止服务

归档前完成：

- 公告停止时间、影响用户和替代服务；
- 停止新写入、导出用户数据、撤销 Key 或 Secret 和关闭任务；
- 按保留规则删除或匿名化生产数据、备份和日志；
- 释放域名、证书、云资源和第三方账户，防止域名或包名接管；
- 仓库标记只读，README 写明最后状态、许可证、已知漏洞和迁移路径；
- 保留必要源码、NOTICE、发布摘要和决策历史。

项目停止维护不允许删除第三方归属或掩盖衍生来源。

## 治理审计

每个 Preview 发布周期检查：

- 项目 owner、维护状态和安全联系方式；
- 身份、账本和数据真值是否唯一；
- 公共契约、消费者和弃用状态；
- AGPL 源码入口、NOTICE、第三方清单和品牌资产；
- 生产域名、Secret、备份、恢复和发布权限；
- 未维护扩展、依赖漏洞和上游许可证变化；
- 文档中的当前状态是否与真实验收一致。

审计发现的问题进入 `architecture-review.md` 或具体项目 Issue，并有 owner、优先级和退出条件。审计报告不包含 Secret、个人信息或可直接攻击生产的细节。
