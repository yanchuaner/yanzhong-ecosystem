# 燕中生态治理仓运行规范

本文说明 `yanzhong-ecosystem` 如何作为跨项目真值仓库运行。项目职责与调用关系见 `architecture.md`，协作流程见 `agent-guide.md`。

## 仓库职责

治理仓拥有：

- 生态级 `AGENTS.md`、愿景、架构、契约、ADR 和阶段状态；
- 品牌、许可、开源、安全、计费、观测和扩展规则；
- 跨系统 JSON Schema 与负向 fixture；
- 正式项目注册表 `repos.yaml`；
- 治理校验器、CI 和贡献入口。

治理仓不拥有项目源码、生产配置、项目锁文件、部署产物或用户数据。七个项目目录是独立 Git checkout，由根 `.gitignore` 排除；禁止把它们提交为嵌套仓库、Git submodule 或 vendored 源码。

## 注册表

`repos.yaml` 只登记相对稳定的项目事实：仓库地址、默认分支、产品职责、权威数据、集成依赖、文档入口、品牌扫描面、许可元数据和发布清单。阶段、完成度、发布结果和临时风险不进入注册表，继续以 `燕中生态项目关系.txt` 为唯一真值。

注册表变更必须满足：

- 项目 ID、目录和远端唯一；
- 每类权威数据只有一个所有者；
- 集成依赖指向已登记项目且不存在环；
- 自主许可为 `AGPL-3.0-only`；
- 路径保持仓库相对路径，不能越出项目目录；
- 新项目同时补职责、关闭方式、维护责任和架构入口。

结构由 `schemas/repository-registry.v1.schema.json` 校验，跨条目不变量由 `validate.py` 校验。

## 校验模式

| 模式 | 命令 | 适用范围 |
| --- | --- | --- |
| 独立 | `make check` | 治理仓自身、注册表、链接、品牌、写作、Schema、CI 与空白字符 |
| 工作区 | `make check-workspace` | 独立模式加七个项目的治理入口、许可、发布脚本、品牌面、远端和差异检查 |
| 自动 | `.venv/bin/python docs/validate.py` | 全部项目存在时用工作区模式，全部不存在时用独立模式 |

自动模式发现只存在部分项目时失败。需要刻意只检查治理仓时显式使用 `--mode standalone`，不能把不完整工作区伪装成完整审计。

## 本地工作区

首次进入治理仓执行 `make setup`，依赖安装到根 `.venv`，版本与哈希由 `requirements.txt` 固定。`make workspace-bootstrap` 根据注册表只克隆缺失项目，已存在目录不会被覆盖；`make workspace-status` 显示各项目分支与脏状态，但不会修改项目。

根 `git status` 只表示治理仓状态。跨仓任务必须同时查看 `make workspace-status` 和每个受影响仓库的详细差异；提交、分支、远端与发布仍逐仓处理。

## CI 与合并

GitHub Actions 只以独立模式验证治理仓，不在每次 PR 克隆所有项目。工作流使用只读令牌权限、固定 Action 提交、锁定 Python 依赖和超时。跨仓实现的合同测试仍由提供方与消费者项目 CI 执行，并在 PR 中链接结果。

`main` 已启用分支保护：变更必须通过 PR，分支必须保持最新，`Validate governance repository` 必须成功，评审对话必须解决，并保持线性历史；管理员同样受规则约束，禁止强推和删除。当前只有一个公开维护账号，因此审批数暂为 0，避免把自我审批伪装成独立复核；补充备份维护者后再提高审批门槛。仓库只允许 Squash 合并，并在合并后自动删除来源分支。

远端同时启用 Dependabot 漏洞告警与安全更新、Secret Scanning、Push Protection 和私密漏洞报告。`CODEOWNERS` 只用于评审路由，不授予生产、发布、安全或法律权限；平台控制也不能替代项目内的鉴权、脱敏、供应链审计和凭据轮换。

## 契约发布

治理文档可随提交演进；被项目直接消费的 Schema 必须以不可变提交 SHA 或正式版本标签引用。破坏性 Schema 变更新建主版本文件，不能覆盖旧版本含义。API、AI 与 Web 完成固定版本消费和合同测试前，仓库建立不等于运行时契约已经闭环。
