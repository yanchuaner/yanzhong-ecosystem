# 燕中生态协作指南

本文定义跨仓库工程变更的执行流程。具体代码规则以目标仓库 `AGENTS.md` 为准。

## 变更分类

| 类型 | 示例 | 必须先确认 |
| --- | --- | --- |
| 项目内部 | 页面、局部服务、仓储实现 | 本仓架构与测试 |
| 契约变更 | API 字段、错误码、事件、消息信封 | `contracts.md`、消费者清单、兼容策略 |
| 架构变更 | 数据所有权、模块边界、设施替换 | 根架构与 ADR |
| 品牌变更 | Logo、产品名、核心 metadata | `brand.md`、来源和法律声明 |
| 高风险运行变更 | 迁移、Secret、生产发布 | 备份、验收、回滚和明确授权 |

## 标准流程

### 1. 建立事实

- 查看所有相关仓库的工作区状态，保留已有修改。
- 阅读根级架构、契约、审查与阶段真值。
- 从代码确认真实调用、数据写入和失败路径，不以 README 代替实现。
- 列出提供方、消费者、数据所有者和第三方依赖。

### 2. 收口契约

- 跨仓变更先修改语义契约或 ADR，再修改实现。
- 明确版本、鉴权、幂等、超时、重试、错误、观测和撤销。
- 提供方先兼容旧消费者；消费者完成迁移前不删除旧字段或端点。
- 数据迁移必须说明双写、回填、一致性检查和回滚。

### 3. 分仓实现

依赖顺序默认是：

```text
契约/schema → API 提供方 → AI/应用服务 → Web/小程序/CLI 消费者 → 文档与示例
```

每个仓库使用独立分支和 PR。不得通过跨仓复制相同类型或临时直读数据库缩短排期。

### 4. 验证

验证分四层记录：

1. 静态检查与单元测试；
2. 提供方/消费者契约测试；
3. 隔离环境真实链路；
4. 生产发布后观察。

低层通过不代表高层通过。使用真实上游或生产数据时必须单独获得授权并遵守数据边界。

### 5. 交付

- PR 说明目的、契约影响、数据影响、验证、已知限制和回滚。
- 同步项目文档；阶段事实只更新根状态真值。
- 发布物包含追溯标识；临时包、日志、测试数据和后台进程在结束前清理。

## 契约评审清单

- 谁拥有该字段或事件？
- 标识符是否稳定且不含个人信息？
- 是否区分缺省、空值和显式零值？
- 失败是否有稳定错误码和 HTTP/事件终态？
- 重试是否会重复写入、重复调用或重复扣费？
- 取消、超时、断流和部分成功如何处理？
- 是否传播 request ID、trace ID 和幂等键？
- 旧消费者如何迁移，何时可以移除兼容层？
- 日志和追踪是否可能泄露正文或凭据？
- schema、fixture 和契约测试由谁维护？

## 模块评审清单

- 领域逻辑是否位于路由或页面组件中？
- 供应商/框架字段是否泄漏到领域对象？
- 新抽象是否有真实实现或消费者？
- 扩展点是否声明权限、成本、副作用和资源限制？
- 工作流是否绕过网关、账本或审计？
- 存储实现能否替换，数据是否带 schema 版本？
- 模块失败是否可降级，是否错误吞掉了计费或权限失败？

## Git 与 PR

- 分支前缀：`feat/`、`fix/`、`docs/`、`refactor/`、`chore/`、`test/`、`ci/`。
- 一个 PR 只处理一个可独立回滚的主题。
- 跨仓变更分别提交 PR，并在描述中互相链接和标出合并顺序。
- 不直接推送受保护分支，不改写共享历史，不删除他人分支。
- 使用仓库现有 PR 模板和上游贡献约定。

## 文档与语言

- 规范写当前有效规则；计划写顺序与退出条件；历史记录写当时证据。
- 避免“暂时先这样”“后面再优化”等无责任边界表述；改写为明确限制、风险和触发条件。
- 不复制状态段落到多个 README。项目 README 只提供定位、运行和文档入口。
- 中文为主要协作语言；代码标识、协议字段和标准错误码使用稳定英文。
